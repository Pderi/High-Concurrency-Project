## 1. 撰写原则（先看这个）

### 1.1 格式模板

每条项目经历建议固定四段结构，与常见简历项目块一致：

```text
【项目名称】（角色定位）
项目简介：1～2 句话说明业务场景 + 你的职责边界。
技术栈：Spring Boot 3 + ……（按 JD 微调顺序，把对方关心的放前面）
· 【6～10 字专业总结】：手段 + 量化结果（每条 1～2 行）
· ……
```

**单条结构示例：**

```text
· 设计 Redis 异步抢票链路：以 Lua 原子预扣 → MQ 削峰建单 → MySQL 落库构建分层峰值路径，
  单票档压测 3000+ QPS 零超卖。
```

**前缀好 / 坏对照：**

| 不推荐（空泛） | 推荐（动词 + 具体技术/机制） |
| --- | --- |
| 设计抢票链路 | 设计 Redis 异步抢票链路 |
| 优化元数据读 | 设计元数据缓存预热机制 |
| 保障库存正确 | 设计幂等占用关单机制 |
| 落地流量治理 | 搭建限流全链路观测体系 |
| 实践微服务化 | 拆分 Spring Cloud 微服务架构 |

### 1.2 写法要点

| 要点 | 说明 |
| --- | --- |
| **前缀总结** | 每条以 **6～10 字「动词 + 技术/机制名」** 起头；对标版专「设计多级缓存方案」、张江「集成 Flowable 工作流」的粒度 |
| **前缀要具体** | 写出 Redis / Outbox / ShardingSphere / Saga 等关键词，避免「抢票链路」「库存正确」等空词 |
| **详述不重复前缀** | 冒号后展开手段与结果，不要与前缀同义反复 |
| **手段要具体** | 写「Redis Lua 原子预扣」而非「用了 Redis」 |
| **结果要可量化** | 响应时间、QPS、超卖率、卡单率、SQL 次数等；压测数据可写区间 |
| **边界要诚实** | 模拟支付、无选座、无多地多活——面试时能一句话讲清 |

## 2. 完整版项目经历（推荐直接粘贴后微调）

### 高并发抢票票务平台（独立设计与全链路落地）

**项目简介：** 自研大麦类票务抢票系统，支持演出/场次/票档管理、开售峰值抢票、待支付占用、模拟支付与电子票、超时关单释放库存。负责从需求分析、数据库设计、核心抢票链路、流量治理到分库分表与微服务拆分的**端到端设计与实现**，并提供 k6 压测与 Prometheus 观测方案。

**技术栈：** Java 17 · Spring Boot 3 · Spring Cloud Gateway · OpenFeign · RocketMQ · Redis · MyBatis-Plus · MySQL 8 · ShardingSphere-JDBC · Resilience4j · Micrometer · Docker · k6

· 设计 Redis 异步抢票链路：以 Lua 原子预扣 → RocketMQ 削峰建单 → MySQL 条件更新 `sold_stock` + 库存流水构建分层峰值路径，客户端以受理令牌 + 轮询拿单替代同步阻塞；单票档压测峰值 **3000+ QPS** 下 MySQL 写压可控，**零超卖**。

· 设计元数据缓存预热机制：联动管理端写路径，DB 变更后主动写入 Redis 并级联 `warmSession` 预热，使开售高峰元数据读稳定命中缓存；余票口径仍直查 DB 权威数据，规避缓存与库存语义混用引发的一致性问题。

· 设计幂等占用关单机制：基于 `idempotency_key` 与唯一索引落地抢票幂等，按用户维度校验限购；明确 `sold_stock` 待支付占用语义，以超时关单 Job（Redis 分布式锁互斥）回退占用并回补 Redis 余量，贯通占-付-关-释完整状态机。

· 落地 Outbox 可靠消息投递：引入本地消息表与业务落库同事务，异步投递 RocketMQ 并在消费端以业务键幂等；配合失败重试、死信与关单/对账补偿形成闭环，跨服务链路以 Saga + 幂等步骤保证最终一致，避免峰值路径依赖 2PC。

· 搭建限流全链路观测体系：接入 Resilience4j 抢票限流与 Gateway 统一入口限流，将 `traceId` / `orderNo` 写入 MDC；通过 Micrometer 暴露预扣结果、建单延迟、关单量等核心指标，并编写 k6 压测脚本输出报告，支撑瓶颈定位。

· 实施订单分库读写分离：引入 ShardingSphere-JDBC，对订单/流水按 `user_id` 落地 **2 库 × 2 表** 分片并配置主从读写分离；C 端订单列表默认走从库，建单/支付/关单强制主库，复制延迟场景下对「我的订单」提供强制主读兜底。

· 拆分 Spring Cloud 微服务架构：按展示目录、订单交易、库存票档拆分独立服务，以 `*-api` 契约与 `*-server` 实现解耦；Gateway 统一路由，OpenFeign 承担同步调用、RocketMQ 承担异步解耦，数据库按服务隔离，提升可维护性与水平扩展能力。

· 建立库存流水对账补偿：实现定时对账 Job，比对 `sold_stock`、有效订单占用与 Redis 余量，偏差写入 `tkt_stock_ledger` 并触发告警；管理端关键写操作落审计表，支撑库存异常与操作行为追溯。

## 3. 精简版（版面紧张时用，保留 4～5 条）

### 高并发抢票票务平台（核心开发）

**项目简介：** 票档级库存抢票系统，含管理端 CRUD、C 端浏览、峰值抢票、模拟支付与关单对账。

**技术栈：** Spring Boot 3 · Redis · RocketMQ · MySQL · MyBatis-Plus · Resilience4j · ShardingSphere-JDBC

· 设计 Redis 异步抢票链路：以 Lua 预扣 + MQ 异步建单 + MySQL 乐观更新构建全链路，单票档压测 **3000+ QPS** 无超卖。

· 设计元数据缓存预热机制：联动管理端写路径实现 Redis 预热与写后主动刷新，开售高峰读路径达毫秒级；余票与占用口径以 DB 为准。

· 设计幂等占用关单机制：落地 Outbox + 幂等消费保障建单最终一致，配合超时关单分布式锁、库存回补与对账 Job 形成补偿闭环。

· 实施订单分库读写分离：引入 ShardingSphere 完成分表与读写分离，拆分展示/订单/库存微服务，以 Gateway + Feign + MQ 构建三层通信模型。

· 搭建限流全链路观测体系：接入 Resilience4j 限流、traceId 追踪、Prometheus 核心指标与 k6 压测脚本，支撑容量评估。

## 4. 按能力拆条（便于替换 / 组合）

若目标 JD 强调某一方向，可从下表挑 1～2 条替换完整版中的同类条目。

### 4.1 高并发 / 性能

```text
· 改造 Redis 异步峰值路径：针对抢票写突发将同步落库改为「Redis 闸门 + 异步建单」，使峰值流量主要停留在 Redis/MQ，
  单票档压测 QPS 由同步方案的 ~200 提升至 3000+，P99 建单延迟下降约 60%。
```

```text
· 优化 Lua 原子预扣性能：编写 Lua 脚本合并「校验余量 + DECR」为单次原子操作，减少 Redis 往返；
  配合受理令牌短轮询，预扣接口平均响应稳定在 50ms 以内（不含轮询等待）。
```

### 4.2 缓存

```text
· 设计三层 Redis 读模型：构建元数据 / 库存闸门 / 受理结果三层缓存，元数据配置 7 天 TTL 并随管理端写操作预热；
  开售完成后元数据读命中率 >95%，避免高峰回源 MySQL。
```

### 4.3 一致性与补偿

```text
· 实现超时关单库存释放：定义 sold_stock 占用语义（待支付 + 已支付），以关单 Job 小批量事务释放占用并写流水；
  多实例部署下以 Redis 锁保证关单幂等，重复执行率为 0。
```

```text
· 建立库存流水对账补偿：实现每日对账 Job，比对 DB sold、有效订单占用与 Redis remain，自动写入「对账修正」流水，
  上线后库存偏差事件归零。
```

### 4.4 消息队列

```text
· 落地 RocketMQ 事务消息投递：采用事务消息 / Outbox 表与订单 insert 同库同事务，解决「库成功消息丢失」问题；
  消费端以 idempotency_key 去重，在至少一次投递语义下仍保证业务幂等。
```

### 4.5 分库分表 / 读写分离

```text
· 实施 ShardingSphere 订单分片：按 user_id 哈希将订单表、流水表拆分为 4 片（2 库 × 2 表），以雪花算法生成全局 order_no；
  管理端跨分片分页走 ES / 广播表方案，业务代码经 ShardingSphere 无感路由。
```

```text
· 配置 MySQL 主从读写分离：列表读走从库，支付/关单等强一致读注解强制主库；
  复制延迟 >500ms 时对「刚支付完查单」自动降级主库读，避免用户看到旧状态。
```

### 4.6 微服务

```text
· 拆分 Saga 跨服务建单链路：拆分展示服务（读多易缓存）、订单服务（状态机 + 关单）、库存服务（tier + ledger）；
  跨服务建单采用 Saga 编排：预扣成功 → 创建订单 → 失败则发布补偿事件回补 Redis。
```

### 4.7 治理与压测

```text
· 自研 Gateway 多维限流组件：接入 Gateway 全局限流 + 应用内 Resilience4j 抢票接口限流 + 用户维度令牌桶（可选扩展）；
  恶意刷接口场景下 DB 连接池使用率下降 70%+。
```

```text
· 建立 k6 压测验收规范：编写压测 SOP，覆盖单档售罄、幂等重放、关单回补三类场景；
  输出 TPS、P95/P99、错误率与 Prometheus 截图，作为答辩与面试材料。
```

## 7. 面试追问预备（每条经历配 1 句备用）

| 可能追问 | 建议答法（摘要） |
| --- | --- |
| 为什么 Redis 预扣还要写 DB？ | Redis 扛峰值闸门，DB 是权威账本；最终以 sold_stock + ledger 为准，Redis 可重建。 |
| 预扣成功但建单失败怎么办？ | 消费失败重试 + 超限进 DLQ；定时扫描 PENDING 受理 + 关单/补偿回补 Redis。 |
| 会不会少卖？ | 预扣成功即占名额；少卖只可能 Redis 比 DB 紧，对账 Job 会纠偏并告警。 |
| 为什么不用 Seata？ | 峰值路径要短；Outbox + 幂等 + Saga 补偿足够，且更易压测和排障。 |
| 分片后跨用户查订单？ | 管理端走聚合查询或 ES；C 端按 user_id 路由，天然单分片。 |
| 和真实大麦差在哪？ | 无选座、模拟支付、单地域；核心「不超卖 + 异步落库 + 关单释放」同构。 |

## 8. 不建议写 / 慎写的内容

| 避免 | 原因 |
| --- | --- |
| 「实现多地多活」「完整支付清结算」 | 超出项目边界，易被深挖穿帮 |
| 「QPS 10 万+」无压测支撑 | 个人项目环境难以自证 |
| 「自研分布式事务框架」 | 过度包装；讲清 Outbox/Saga 即可 |
| 把所有中间件平铺堆砌 | HR 扫一眼看不出你的贡献 |
| 不写关单/对账只写抢票 | 库存占用语义是亮点，省略会显得方案不完整 |

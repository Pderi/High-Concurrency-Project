## 2. 项目背景与建设目标

### 2.1 背景

大型演出、体育赛事等票务开售时，往往在极短时间内产生**读放大、写突发、热点场次与热点票档**，形态与电商秒杀、限时抢购高度相似，但更接近「交易类」业务：除库存扣减外，通常还存在**下单占位、支付倒计时、超时释放库存**等闭环。现实产品如大麦、猫眼等均在此类场景上做了长期工程投入。

本学习/项目目标**对齐大麦类抢票的体验与压力特征**，但在范围上采用**可落地的简化模型**（见第 3.3 节），以便在可控复杂度内完成全链路高并发设计。

### 2.2 建设目标

1. **业务目标**：支撑运营侧配置演出与场次、票档与库存；用户在开售窗口内发起抢票并形成订单；在支付时限内完成支付（或模拟支付）；超时未支付释放占用的库存；订单与票务状态可查询、可审计。
2. **技术目标**：用一套可演示、可压测的**全链路高并发设计**覆盖：接入与流量治理、应用无状态扩展、缓存与削峰、MySQL 与一致性策略、异步建单与消息消费、库存占用与释放、监控与运维。**代码实现阶段**须遵循仓库内《通用架构设计与代码结构规范》《CRUD开发流程规范》的分层与 CRUD 流程。

### 2.3 成功标准（摘要）

- 在既定容量假设下，核心「抢票/下单」接口满足约定的峰值 QPS、P99 延迟与错误率上限；**不超卖**（在业务规则允许范围内）；订单与库存状态可追溯、可对账；支付超时后库存可被后续用户正常使用。

## 3. 业务方向说明与选型理由

### 3.1 业务命名与定位

**正式名称**：高并发抢票票务平台（项目内可简称「简票」或「抢票 Demo」，对外说明为**大麦类场景的简化实现**）。

**一句话描述**：运营在管理端维护演出、场次、票档与库存；用户在开售时抢购某票档名额；系统在网关与应用层控流，在内存/缓存侧完成原子预扣或占位，通过消息队列异步创建订单；用户在支付时限内完成支付（或模拟支付），否则订单关闭并**释放库存**；最终生成可查询的订单与电子票/凭证状态。

### 3.2 为何覆盖「全链路」高并发设计

| 链路层次 | 在本业务中的落点 |
| --- | --- |
| 客户端与边缘 | 场次详情页静态资源、开售倒计时、防重复点击；减轻瞬时集中 |
| 接入层 | API 网关鉴权、路由、全局限流、用户/IP 频控 |
| 应用层 | 无状态服务、线程池与超时、熔断降级、抢票编排（下单、支付、关单） |
| 缓存与分布式协调 | 场次/票档库存缓存、原子扣减或占位、热点 Key 治理、分布式锁/Lua（设计阶段选型） |
| 消息与异步 | 抢票请求异步化、削峰、幂等消费、重试与死信 |
| 数据层 | MySQL 存权威订单、库存流水与票档；索引与乐观控制；读写分离与分库分表作为演进预留 |
| 可观测与运维 | 指标、日志、链路追踪；压测；对账（缓存/DB/订单状态） |

该业务同时具备**高并发读**（场次列表、详情、余票展示）与**高并发写**（开售瞬时抢票），并引入**订单 + 支付超时 + 库存回滚**，比纯「领券」更接近真实票务与交易链路。

### 3.3 范围边界声明（重要）

**首期必须包含（MVP 核心）**

- **票档级库存**：按「场次 + 票档（如 VIP / 看台 A / 看台 B）」维护库存数量，**不做真实座位图、不做逐座位锁**（与完整大麦选座系统区分）。
- **抢票 → 订单待支付 → 支付成功 / 超时关闭**：须实现**支付倒计时**（时长可配置）；超时订单关闭并**释放对应票档库存**（实现方式属设计阶段，需求上必须满足业务结果）。
- **支付**：可采用**模拟支付接口**（学习项目推荐），但订单状态机与超时逻辑须完整；若对接真实支付，作为后续阶段。

**首期不包含（刻意裁剪）**

- **选座**：座位图、单座锁定、视觉区域定价等，列为二期或扩展需求。
- **复杂实名制与公安核验**：不作为首期阻塞项；可预留证件号字段或全部 mock。
- **完整清结算、分账、退票改签规则引擎**：首期不实现生产级规则，仅保留简化退票/关闭入口（可选）。

**合规说明**：本项目以**技术学习**为主，不承诺具备商用票务资质与法务完备性。

## 4. 术语与角色

| 术语 | 说明 |
| --- | --- |
| 演出 | 一场文化/体育活动的顶层实体，如某歌手巡回演唱会（可含多场次） |
| 场次 | 具体日期与开场时间的演出单元，用户抢票的基本维度之一 |
| 票档 | 某场次下的票价分区（价格、库存独立），**首期库存以票档为单位扣减** |
| 抢票请求 | 用户对某场次某票档发起的占库存/下单请求（实现可同步返回或异步排队） |
| 订单 | 抢票成功后形成的交易单据，含待支付、已支付、已关闭等状态 |
| 预扣减/占位 | 在缓存或内存侧先占用票量，再异步落库与对齐的过程（实现细节属设计阶段） |
| 电子票/凭证 | 支付完成后用户持有的凭证状态（学习项目可用「凭证码」表示） |
| 运营/管理员 | 使用管理端配置演出、场次、票档与查询数据的一方 |
| C 端用户 | 已登录用户，浏览场次并发起跑票、支付、查单 |

## 5. 用户画像与典型场景

### 5.1 运营人员

- 创建与维护演出、场次、票档；设置开售时间、各票档库存、单人限购张数；发布/下架。
- 查看场次维度统计（下单数、支付成功数、关闭订单数、库存消耗）。
- 异常排障：按订单号、用户 ID、场次 ID 查询；关键操作审计。

### 5.2 终端用户

- 浏览可购演出与场次列表、场次详情（票价、余票策略见下）。
- 在开售时间内对某票档发起抢票；获得「待支付订单」或明确失败原因。
- 在支付时限内完成支付（或模拟支付）；超时则订单关闭。
- 查询本人订单与票务/凭证状态。

### 5.3 典型场景（用户故事）

1. **开售倒计时前**：用户浏览预热页；运营确认场次与库存；系统可做缓存预热（设计阶段定义）。
2. **开售瞬间**：大量并发抢票；限流、防刷、异步积压；用户收到排队中/待支付/售罄等反馈。
3. **待支付**：用户须在 T 分钟内支付，页面展示剩余支付时间。
4. **支付成功**：订单变为已支付，生成电子票/凭证（状态可查询）。
5. **支付超时**：订单自动关闭，库存释放，其他用户可继续抢购。
6. **售罄与下架**：票档库存为 0 时拒绝新抢票；友好提示。

## 6. 功能需求

功能按**管理端（CRUD 与运营）**、**用户端（高并发核心）**、**订单与支付**、**履约与一致性**、**风控与安全**、**观测与运维**划分。优先级见第 10 章。

### 6.1 管理端：演出、场次与票档（贴合 CRUD 规范）

**目标**：为运营提供标准化增删改查能力；字段以《设计文档》为准。

1. **演出管理**：创建、编辑、发布/下架；列表与分页；详情。
2. **场次管理**：隶属于演出；开场时间、场馆名称（文本即可）、开售时间、场次状态；列表与筛选。
3. **票档管理**：隶属于场次；票档名称、单价（学习项目可用分）、库存、单人限购张数；**不支持选座**。
4. **数据约束**：已产生订单的场次/票档，删除策略为逻辑停用或禁止删除（具体规则设计阶段细化）。
5. **统计与查询**：场次/票档维度汇总；订单列表查询（排障）。
6. **权限与审计**：管理操作权限；改价、改库存、改限购等记审计日志。

### 6.2 用户端：浏览与抢票（高并发核心路径）

1. **列表与详情**：可购演出列表、场次详情（含票档价格与**余票参考**，默认允许短延迟，须产品文案标明「仅供参考」或「非实时」）。
2. **抢票接口**：用户对指定场次、票档发起抢票（可带购买张数，不超过单人限购与剩余库存）；须幂等或业务去重，避免连点产生多笔待支付订单（策略设计阶段定）。
3. **返回类型**：至少包括成功（进入待支付并返回订单号）、失败（售罄、未开售、限购、风控拒绝等）、处理中（若采用异步建单）。
4. **订单查询**：用户按订单列表/详情查询状态与支付截止时间。

### 6.3 订单与支付

1. **订单状态机**：至少包含待支付、已支付、已关闭（超时/取消）；非法跳转禁止（设计文档细化）。
2. **支付倒计时**：订单创建时记录支付截止时间；超时触发关单并释放库存。
3. **支付渠道**：首期推荐**模拟支付**（例如调用「确认支付」接口即成功）；预留对接真实支付的扩展点。
4. **关单释放**：超时关单后，对应票档可售库存恢复，不得永久少票（与缓存/DB 对齐策略在设计文档说明）。

### 6.4 履约与一致性

1. **出票/凭证**：支付成功后生成用户可查询的凭证状态（码或状态字段）。
2. **补偿与对账**：定时核对订单状态、票档库存、缓存侧计数；异常进入补偿或告警（阈值在设计文档细化）。
3. **幂等与防重**：消息消费、订单写入使用幂等键（如用户+场次+票档+业务唯一键），防止 MQ 重试导致超卖或多单。

### 6.5 风控与安全

1. **身份认证**：用户端登录；管理端独立鉴权。
2. **防刷与频控**：用户级、IP 级限流；简单验证码或人机校验可作为 Could 项。
3. **数据安全**：敏感信息脱敏；审计日志。

### 6.6 可观测性与运维（需求级）

1. **指标**：抢票接口 QPS、延迟、错误率；消息堆积；关单任务执行情况；DB 慢查询。
2. **链路**：分布式追踪（需求级）。
3. **日志**：关联 traceId、用户 ID、场次 ID、订单号。
4. **压测**：开售峰值场景压测并留存基线（技术文档给目标）。

## 7. 非功能需求

### 7.1 性能与扩展性（目标值为草案，以技术文档为准）

| 类别 | 要求 |
| --- | --- |
| 峰值抢票 QPS | 单场次开售峰值目标在《技术方案》中给出（学习性目标可与实际资源匹配） |
| 读接口 | 场次详情在缓存命中下 P99 由技术文档定义 |
| 扩展性 | 应用无状态水平扩展；数据层支持读写分离与分库分表演进 |
| 一致性 | 票档不超卖；余票展示允许最终一致；**支付超时后库存须可被再次抢购** |

### 7.2 可用性

- 核心链路故障预案：降级策略（如仅展示静态页、暂停抢票按钮）在设计文档列出。

### 7.3 安全

- 常规 Web 安全；管理端强权限；接口防刷（技术方案可选签名、令牌）。

### 7.4 兼容与演进

- 模块边界清晰，便于后续拆分票务服务、订单服务、支付服务。
- 分层与 CRUD 规范同《通用架构设计与代码结构规范》《CRUD开发流程规范》。

## 8. 业务规则汇总（首期必须满足）

1. **开售时间**：仅允许在开售时间之后发起抢票；未开售请求拒绝。
2. **库存**：票档维度总库存不得为负；售罄后拒绝新单。
3. **单人限购**：同一用户对同一场次同一票档的**有效/待支付/已支付**张数不超过配置（具体是否含待支付由设计文档统一，需求上须防刷单）。
4. **订单支付超时**：待支付订单超过支付时限必须关单并释放库存（业务结果必须正确）。
5. **运营改库存/停售**：不得静默吞掉用户已付款订单；未支付与后续请求的行为由设计文档定义，默认**停售后新请求拒绝**。

## 9. 验收标准（测试视角摘要）

1. **功能**：管理端 CRUD；用户浏览、抢票、待支付、支付/超时关单、查单。
2. **并发**：压测下票档不超卖；重复点击不产生非法多余占用。
3. **超时**：大量待支付订单超时后，库存可被后续请求使用。
4. **退化**：缓存/MQ 异常行为符合设计说明。
5. **可观测**：可追踪单次抢票到订单全链路。

## 11. 假设、依赖与风险

### 11.1 假设

- 用户体系与登录可 mock 或对接统一认证。
- 支付为模拟或沙箱，不依赖真实央行/银联链路。

### 11.2 依赖

- 认证、MQ、缓存、MySQL；可选 CDN/OSS 用于静态资源。

### 11.3 风险

| 风险 | 说明 | 应对方向 |
| --- | --- | --- |
| 热点场次单 Key | 超级 IP 场次集中访问 | 分片、本地缓存、合并计数（设计文档） |
| 黄牛与脚本 | 恶意刷单 | 频控、限购、验证码（Could） |
| 体验与一致性 | 余票显示与真实库存短暂不一致 | 产品文案 + 对账 |
| 范围膨胀 | 选座、退票规则拖慢首期 | 严格遵守 3.3 边界 |

## 1. 文档说明

### 1.1 与《技术文档》的关系

- 《技术文档-抢票票务平台》描述**首期**总体架构、选型与核心链路（票档级库存、Redis 预扣、MQ、MySQL 权威落库等）。
- **本文档**在此基础上做两件事：
  1. **能力地图**：按请求类型与系统层次，说明「高并发」在本项目里具体指哪些问题与手段。
  2. **扩展架构**：将分库分表、微服务拆分、分布式一致性、MQ 一致性落到**可讲解、可分期实现**的方案边界，避免名词堆砌或与首期范围混淆。

### 1.2 落地原则（个人项目 / 简历向）

- **分期**：峰值链路（Redis → MQ → DB）与幂等、关单补偿可先跑通；分库分表与多服务可后移或用「双库双表 + 规则演示」降低工程量。
- **主叙事**：最终一致、可靠事件、幂等消费，优于在抢票主路径上强调重型 2PC。
- **诚实边界**：未实现的环节在答辩材料中标注为规划或 WIP，与已跑通链路区分。

## 2. 高并发能力地图（按本项目业务）

### 2.1 流量形态与矛盾

| 类型 | 典型接口 | 高并发下要解决什么 |
| --- | --- | --- |
| 读多写少 | 演出/场次/票档展示 | 缓存、必要时读写分离；余票可为短延迟近似读，减轻 DB |
| 写突发（核心） | 抢票下单 | 瞬时集中写、热点行更新、**不超卖**、保护 MySQL 不顶满峰值 |
| 写平稳 | 模拟支付、管理端 CRUD | 事务正确性、规范与权限；并发相对可控 |
| 批处理 | 超时关单、对账 | 扫表/分批、避免长事务；多实例下避免重复执行 |

### 2.2 接入与边缘

- API 网关：路由、鉴权、统一错误与限流入口。
- 限流 / 熔断（如 Sentinel、Resilience4j）：过载保护，防止单接口拖垮线程池与数据库。
- CDN / OSS（静态）：与动态抢票流量解耦。

对应课题：**边界削峰、过载保护**。

### 2.3 应用层

- 无状态业务实例：水平扩展；会话、幂等依赖 Redis / DB。
- 抢票编排：**分层抗压**（先 Redis / MQ，再 MySQL），异步化。

对应课题：**水平扩展、异步化、责任分层**。

### 2.4 中间件与数据层（与现有方案对齐）

| 组件 | 用途（本项目语境） |
| --- | --- |
| Redis | 票档库存预扣、限流计数、热点标记；Lua 保证原子性、减少往返 |
| MQ（RocketMQ / Kafka 等） | 异步建单、削峰；消费并发与重试策略 |
| MySQL | 订单与票档权威数据；`tkt_tier` 等乐观更新；`tkt_stock_ledger` 流水与对账 |

对应课题：**原子预扣、背压与解耦、热点行更新、最终一致与可审计**。

### 2.5 一致性与正确性（面试与实现重点）

- **不超卖**：Redis 预扣与 DB `sold_stock` / 流水对齐，失败可回补。
- **占用语义**：`sold_stock` 含待支付占用；超时关单释放占用。
- **幂等**：`order_no`、`idempotency_key`、消息消费幂等键、唯一约束。
- **失败可恢复**：死信、关单补偿、`tkt_stock_ledger` 支撑对账与追溯。

### 2.6 可靠性与可观测

- 定时任务 + 分布式锁（如 Redis）：多实例关单/对账不重复执行。
- 全链路：`order_no` / `traceId` 定位一次抢票。
- 压测与容量：目标区间与瓶颈定位。

### 2.7 首期明确不主打的能力（与《技术文档》一致）

选座、真实支付清结算、多地多活、完整风控引擎等——简历与答辩应强调**票档级库存 + 峰值写路径 + 异步落库 + 占用/关单 + 流水**，避免夸大范围。

## 3. 分库分表（如何「涉及」本项目）

### 3.1 典型切分对象

| 对象 | 优先级 | 说明 |
| --- | --- | --- |
| 订单表 | 高 | 量大；可按 `user_id` 或 `order_no` 哈希分表，或按时间分片 |
| 库存流水（如 `tkt_stock_ledger`） | 中高 | 写多、轨迹长；分片键可与订单一致或按 `show_id` 等业务维度 |
| 票档 / 场次 | 一般较低 | 行量相对小；热点更多在单行更新与缓存策略，分表非第一手段 |

### 3.2 与峰值链路的关系

分库分表不改变「Redis 预扣 + MQ + MySQL 权威」的主线，但引入：

- **分片键设计**、全局 ID（雪花等）、跨分片查询策略。
- Outbox / 本地消息表若落库，需与订单等表**同分片**，避免跨库分布式事务。

### 3.3 建议落地深度（个人项目）

- 优先 **单库分表** 或 **ShardingSphere 规则 + 小规模数据** 验证路由与全局 ID。
- 「双库双表」演示跨库订单维度即可，不必一上来超大分片数。
- **细化设计**见 `docs/设计/数据库架构升级-分库分表与读写分离.md`（含读写分离、主从与代码验收标准）。

## 4. 微服务（如何「涉及」本项目）

### 4.1 与 Maven 多模块的关系

多模块（`*-api` / `*-server`）描述**代码边界**；微服务描述**部署与进程边界**。可并存：多仓库或多模块分别打包为独立进程。

### 4.2 建议服务切分（示例，宜控制在约 3 个）

| 服务 | 职责 |
| --- | --- |
| 展示 / 商品服务 | 演出、场次、票档读模型；读多、易缓存 |
| 订单服务 | 下单、订单状态机、关单（与占用强相关） |
| 库存 / 票档服务 | `tkt_tier`、扣减确认、流水写入（亦可与订单合并以控制复杂度） |
| 模拟支付（可选） | 支付回调、幂等，独立小服务便于演示边界 |

### 4.3 配套能力

- 注册发现 / 配置（如 Nacos）。
- API 网关按路由转发到各服务。
- **数据隔离**：至少订单库与展示库分离，才符合微服务常见叙述。

---

## 5. 微服务下的跨服务事务一致性

### 5.1 推荐主叙事：最终一致 + 显式模式

| 场景 | 建议讲法与模式 | 备注 |
| --- | --- | --- |
| 抢票：占库存 + 建订单 | **Saga** 或 **可靠事件（Outbox）** | 避免主链路依赖重型 2PC |
| 支付成功：更新订单 + 写票据 | 单服务内**本地事务**；若跨服务则用 Saga 步骤或可靠事件 |  |
| 强一致跨多库 | 尽量少用 | 峰值路径不宜以 2PC 为主 |

### 5.2 简历可引用的一句话

跨服务采用 **Saga / Outbox（可靠事件）** 保证**最终一致**，关键步骤**幂等**；抢票峰值路径以异步与分层抗压为主，不依赖中心化 2PC。

---

## 6. 消息队列一致性（建议对齐的三件事）

### 6.1 生产者侧

- **事务消息**（如 RocketMQ）或 **Outbox 模式**：业务落库与「待发事件」同事务，再异步投递，避免「库提交了消息没发出去」等不一致。
- 分库分表时，Outbox 表分片键与订单等业务表对齐。

### 6.2 消费者侧

- **至少一次投递**假设下，业务必须**幂等**（业务键 / 唯一约束 / 消费去重表）。
- 与本文档 2.5 节、`idempotency_key` 设计一致。

### 6.3 失败与补偿

- 重试策略、死信队列。
- **关单 / 回补** 定时任务与 **`tkt_stock_ledger`** 对账，形成闭环叙述。

## 7. 推荐总故事线（简历与架构说明）

1. **接入层**：网关 + 限流熔断。  
2. **峰值路径**：Redis Lua 预扣 → **MQ（Outbox / 事务消息）** → 订单落库。  
3. **数据层**：订单与流水分表（可选分库）；票档热点仍以缓存与乐观更新为主。  
4. **微服务**：订单 / 库存(票档) / 展示 等拆分，数据库隔离。  
5. **一致性**：跨服务 **Saga 或 Outbox + 幂等消费**；关单与流水支撑补偿与对账。

---

## 8. 风险与诚实边界

- **Seata AT + 大规模分片 + 过多服务** 对个人项目往往过重；优先 **Outbox + Saga + 幂等** 更易讲清、易落地。
- 文档中「扩展」能力若尚未编码实现，应在 README / 简历中区分**已验证链路**与**规划**，避免面试追问脱节。

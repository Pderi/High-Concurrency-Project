# 数据库架构升级设计：分库分表 · 读写分离 · 主从同步

在 P0～P5 主链路已跑通的前提下，对 MySQL 数据层做**可讲解、可代码演示**的架构升级：引入主从复制语义、读写分离路由，以及对订单/流水等大体量表的分库分表。本文档为设计基线；**不要求**在本机搭完整生产级多机复制集群，后续以 ShardingSphere-JDBC + 多数据源配置 + 演示拓扑在代码侧落地即可。

## 1. 文档目的与边界

### 1.1 目的

1. 明确本项目「数据库架构升级」要覆盖的三类能力及它们如何组合。
2. 给出与票务领域对齐的**分片键、广播表、跨分片查询策略**。
3. 约束后续代码实现的技术选型、模块改动面与验收标准，避免范围膨胀。

### 1.2 范围内

| 能力 | 设计要求 | 代码演示深度（约定） |
| --- | --- | --- |
| 主从同步 | 主写从读的拓扑与复制语义 | 配置上区分 `master` / `slave` 数据源；可用 Docker 双实例或「逻辑主从」（同一 MySQL 两库模拟） |
| 读写分离 | 写走主、读走从（及强制主读场景） | ShardingSphere 读写分离规则 + 注解/提示强制主库 |
| 分库分表 | 订单/流水等按分片键路由 | 至少 **2 库 × 2 表**（或单库 4 表）规则可跑通 CRUD |

### 1.3 范围外（本期不做）

- 真实生产级半同步/组复制运维、自动故障切换（MHA/Orchestrator）完整落地。
- 跨分片分布式事务（强一致 2PC）；跨分片复杂 JOIN。
- 选座、多地多活、分片在线扩容自动化。
- 将 `tkt_tier` 热点行拆成「库存分片」作为第一优先级（热点仍以 Redis 预扣为主）。

### 1.4 与现有结论对齐

- 库存权威仍在 MySQL `sold_stock`；峰值写路径不变：`Redis 预扣 →（可选 MQ）→ 建单落库`。
- 分库分表**不替代** Redis 闸门，只解决订单/流水规模与单库压力演进。
- 能力地图建议：优先「双库双表 + 规则演示」——本文采纳并细化。

## 2. 现状与目标架构

### 2.1 现状（单库）

```text
tkt-server ──► 单一 MySQL（库 ticket）
                 ├── tkt_show / tkt_session / tkt_tier   （目录+库存权威）
                 ├── tkt_order / tkt_ticket              （交易）
                 ├── tkt_stock_ledger                   （流水）
                 └── tkt_admin_audit                    （审计）
```

痛点（演进动机，非当前故障）：订单与流水随活动增长；关单/对账扫表压力上升；读流量（订单列表、管理端查询）与写流量争用同一连接池。

### 2.2 目标逻辑架构

```text
                    ┌─────────────────────────────────────┐
                    │           tkt-server                │
                    │  Service / Mapper（业务无感分片细节） │
                    └─────────────────┬───────────────────┘
                                      │ JDBC
                    ┌─────────────────▼───────────────────┐
                    │     ShardingSphere-JDBC（嵌入式）     │
                    │  · 分片路由  · 读写分离  · 结果归并    │
                    └─────────┬───────────────┬───────────┘
                              │写             │读（默认）
                    ┌─────────▼───┐     ┌─────▼──────────┐
                    │  Primary    │────►│  Replica(s)    │
                    │  主库集群   │复制 │  从库           │
                    │ ds_0 / ds_1 │     │ ds_0_slave ... │
                    └─────────────┘     └────────────────┘
```

说明：

- **主从**：解决可用性与读扩展；复制延迟需在读策略中显式处理。
- **读写分离**：在主从之上做流量分流。
- **分库分表**：在主库侧（及对应从库镜像）按规则拆分大体量表。

三者关系：**主从是物理/拓扑基础 → 读写分离是流量策略 → 分片是数据布局**。代码层用同一套中间件（建议 ShardingSphere-JDBC）配置表达。

## 3. 主从同步设计

### 3.1 角色与职责

| 角色 | 职责 | 本项目约定 |
| --- | --- | --- |
| Primary（主） | 全部写入、DDL、需要强一致的读 | 建单、支付、关单、`sold_stock` 更新、流水写入 |
| Replica（从） | 异步复制主库变更；承接读流量 | C 端「我的订单」列表、管理端订单分页、演出目录只读（若未命中缓存） |

### 3.2 复制语义（设计假设）

- 默认 **异步复制**（MySQL binlog row 模式）：从库可落后主库数十毫秒～数秒。
- 演示环境允许两种实现之一：
  1. **真主从**：Docker Compose 起 `mysql-primary` + `mysql-replica`，配置 `REPLICATION`。
  2. **逻辑主从**：单机两个 MySQL 实例或同实例两套库，应用侧只配置读写分离规则，复制用脚本/定时同步或文档说明「生产应对齐 binlog」——**代码与配置结构不变**。

### 3.3 与业务的一致性点

| 场景 | 是否允许读从 | 说明 |
| --- | --- | --- |
| 抢票建单后立刻查单 | **否（强制主）** | 避免复制延迟导致「刚下单查不到」 |
| 支付后查电子票 | **否（强制主）** | 同上 |
| 「我的订单」列表（非刚写） | 是 | 可接受短暂延迟 |
| 演出/场次浏览 | 是（或仍走 Redis 元数据） | 读多；元数据已有 Redis 预热 |
| 关单 Job / 对账 Job | **强制主** | 扫待支付、改状态、改 sold，禁止走从 |
| 管理端改票档库存 | 写主；随后读强制主 | 写后读一致性 |

## 4. 读写分离设计

### 4.1 路由规则

```text
默认：写 → Primary；读 → Replica（负载均衡，如 round_robin）
例外：Hint / 注解 / 事务内 → 强制 Primary
```

### 4.2 强制主库策略（代码约定）

建议在后续实现中提供统一能力（择一或组合）：

1. **事务绑定**：`@Transactional` 内全部走主（ShardingSphere 默认行为需核对版本配置）。
2. **显式 Hint**：如 `HintManager.setWriteRouteOnly()` 或项目封装 `@ReadWrite(forceMaster=true)`。
3. **按方法清单**：`OrderGrab/Pay/Close/Reconcile` 写路径与写后读一律主库。

### 4.3 负载与降级

| 策略 | 说明 |
| --- | --- |
| 从库不可用 | 读失败可降级到主（配置开关）；演示默认降级开启，避免本地从库未起导致全挂 |
| 权重 | 多从时可配置权重；演示单从即可 |
| 连接池 | 主从各自 Hikari 池，防止读打满拖死写 |

### 4.4 不读写分离的数据源

分片中间件自身的元数据、以及仅本地演示用的 H2 等——本期不涉及。

## 5. 分库分表设计

### 5.1 表分类

| 类别 | 表 | 策略 | 理由 |
| --- | --- | --- | --- |
| **分片表** | `tkt_order`、`tkt_ticket`、`tkt_stock_ledger` | 按分片键路由到多库多表 | 行数增长快、写多 |
| **广播表** | `tkt_show`、`tkt_session`、`tkt_tier` | 每个分片库保留全量副本 | 行数小；建单/校验常要关联；`tkt_tier` 热点更新需广播写或「单库存库」特判 |
| **单库表（可选）** | `tkt_admin_audit` | 固定落 `ds_0` | 审计量可控；避免无意义扩散 |

> **关于 `tkt_tier`**：票档行少但写热点高。推荐两种方案择一（实现前拍板，默认 **A**）：  
> - **A（推荐演示）**：`tkt_tier` 作为**广播表**，所有分片库各有一份；更新走广播；与现网「单行权威」一致，实现简单。  
> - **B（进阶）**：独立「库存库」不分片，仅订单/流水分片；代码多一套数据源绑定，演示成本更高。

### 5.2 分片键选择

| 候选 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| `user_id` | 「我的订单」天然单分片；限购统计易落同片 | 管理端按 `order_no` 查需二次路由或二次索引表 | **订单/票主选** |
| `order_no` 哈希 | 按单号查询友好 | 用户维度列表易变跨片 | 可作为二级路由辅助 |
| `tier_id` / `session_id` | 场次维度聚合易 | 用户订单列表跨片；与 C 端主路径不符 | 不采用 |

**定案（演示默认）**：

- `tkt_order`、`tkt_ticket`：**分片键 = `user_id`**
- `tkt_stock_ledger`：**分片键 = `tier_id` 哈希** 或与订单同用 `user_id`（若流水必带 user）  
  - 当前流水 DO 无 `userId` 字段 → **推荐按 `tier_id` 分片**，并对账 Job 按票档维度扫（与现 `StockReconcileService` 一致）。  
  - 若希望流水与订单同片：建单写流水时冗余 `user_id` 并改分片键（表结构小改，需记入实现任务）。

**演示定案补充（最小改表）**：

- 订单 / 电子票：`user_id`
- 库存流水：保持现状字段，**按 `tier_id` 分片**（对账/关单按 tier 或 order 已定位到片）

### 5.3 分片算法与拓扑（演示规模）

```text
逻辑库：ticket_logic
物理：
  ds_0 → 库 ticket_0
  ds_1 → 库 ticket_1

分表（以 order 为例）：
  tkt_order_0, tkt_order_1   （每库 2 张表，或每库 1 张表）

算法示例：
  db  = user_id % 2
  table = (user_id / 2) % 2     // 若每库 2 表
  或仅分库：table 固定 tkt_order，db = user_id % 2
```

**首期代码演示推荐（降低复杂度）**：

- **2 库 × 每库 1 套逻辑表名**（ShardingSphere 实际映射 `tkt_order` → 各库同名表），即 **只分库、不分表**；或 **单库 4 表** 只演示分表。  
- 文档与配置预留「库表双分」表达式，实现阶段二选一打勾即可。

默认实现选项（待编码确认）：**2 数据源（ds_0/ds_1）+ 订单按 user_id 分库，表名不分**。

### 5.4 全局唯一与主键

| 字段 | 现状 | 升级后 |
| --- | --- | --- |
| `id` BIGINT 自增 | 单库自增 | **分片后自增不保证全局唯一** |
| `order_no` | 应用生成 `TKT+时间+随机` | 保持应用侧全局唯一；可升级雪花/号段 |
| `ticket_no` | 应用生成 | 同上 |
| `idempotency_key` 唯一索引 | `(user,session,tier,key)` | 同分片内唯一即可（键含 user_id，天然同片） |

**定案**：业务主键继续用 `order_no` / `ticket_no`；表 `id` 改为 **雪花算法（应用生成）** 或各库号段，避免跨库 id 冲突。实现期替换 MyBatis-Plus 自增策略。

### 5.5 跨分片查询策略

| 查询 | 策略 |
| --- | --- |
| 按 `user_id` 分页「我的订单」 | 单分片，精确路由 |
| 按 `order_no` 查单 | **方案**：order_no 编码嵌入 user 分片信息；或二级索引表 `tkt_order_route(order_no,user_id)`（广播或单库）；或全分片并行查（演示可接受、生产慎用） |
| 关单扫「过期待支付」 | **问题**：无 user_id 条件 → 需**全分片遍历** + 每片批处理；Job 加分布式锁保持不变 |
| 对账按 tier | 流水按 `tier_id` 分片则可路由；`sold_stock` 在广播表/`tkt_tier` 上更新 |
| 管理端订单分页（无用户） | 全分片归并分页（ShardingSphere 支持有限）或限制必须带 `user_id`/`order_no` |

**按 order_no 查单的推荐演示方案**：

- 短期：`order_no` 生成规则增加分片后缀或可逆编码（如末尾带 `user_id % N`），解析后精确路由。  
- 或维护极简 `order_route` 表（单库）。

### 5.6 与抢票主链路的衔接

```text
grab 预扣 Redis（不分片）
  → createOrder：
       写 tkt_order（路由 user_id）
       更新 tkt_tier.sold_stock（广播表写所有节点 / 或库存库）
       写 tkt_stock_ledger（路由 tier_id）
  → 支付：同 user_id 片写 ticket
  → 关单：定位订单所在片 → 减 sold（广播）→ 回补 Redis → 写流水（tier 片）
```

注意：广播表更新 `tkt_tier` 时，ShardingSphere 会向多数据源写；需保证失败可重试，避免各库 sold 不一致——对账 Job 仍以「有效订单合计」为权威纠偏（现逻辑可保留，改为逐库/逐片执行）。

## 6. 技术选型

| 项 | 选型 | 理由 |
| --- | --- | --- |
| 分片 & 读写分离中间件 | **ShardingSphere-JDBC 5.x**（嵌入进程） | 与 Spring Boot 3 / MyBatis-Plus 常见集成；无需独立 Proxy 进程即可演示 |
| 主从 | MySQL 8 复制 或 逻辑双源 | 与现 `docker-compose` 可扩展 |
| 配置形态 | `application-sharding.yml` + profile `sharding` | 默认单库 profile 不变，避免破坏现有本地体验 |
| ORM | 继续 MyBatis-Plus | Mapper SQL 尽量带分片键；禁止无键的隐式全表扫描（Job 显式广播） |

备选（不采用除非有强需求）：ShardingSphere-Proxy（多一运维面）、自行抽象多数据源（重复造轮子）。

## 7. 配置与环境拓扑（演示）

### 7.1 Profile 建议

| Profile | 行为 |
| --- | --- |
| `local`（默认） | 单库，与现网一致 |
| `sharding` | 启用 ShardingSphere：分库 + 读写分离规则 |
| `sharding` + Compose | 可选拉起 primary/replica 与 ticket_0/ticket_1 |

### 7.2 Docker Compose 目标形态（示意）

```text
mysql-primary-0   :3307  → ticket_0（主）
mysql-primary-1   :3308  → ticket_1（主）
mysql-replica-0   :3309  → 复制 primary-0（从）
mysql-replica-1   :3310  → 复制 primary-1（从）
redis             :6379
```

最小可演示（允许裁剪）：

```text
# 最小：2 主库，无从库 —— 读写分离把「从」指回主（规则在，延迟为 0）
# 或：1 主 1 从 + 仅分表（单库多表）
```

**编码阶段默认最小集**：2 个 JDBC URL（ds_0/ds_1）指向同机不同库；读写分离的 slave 可先指向同一 URL，配置结构保留，文档标明生产换成真从库。

### 7.3 配置项草案（逻辑）

```yaml
# profile=sharding 时生效（示意）
spring:
  # 实际由 ShardingSphere 接管 DataSource
mode: Standalone

tkt:
  sharding:
    enabled: true
    db-count: 2
    # order 分片键 user_id
  readwrite:
    enabled: true
    force-master-on-write-transaction: true
```

## 8. 代码落地规划（设计 → 实现映射）

> 本文只定设计；确认后再编码。下列为建议实现切片。

| 步骤 | 内容 | 验证 |
| --- | --- | --- |
| S1 | 引入 ShardingSphere-JDBC；`sharding` profile；2 库初始化脚本（广播表+分片表） | 启动成功，单用户下单路由到固定库 |
| S2 | 订单/票按 `user_id` 分库；流水按 `tier_id` 分库 | 两用户落不同库；按 user 查单不串库 |
| S3 | 读写分离规则 + 写后读强制主 | 配置项可切换；关单/支付走主 |
| S4 | `order_no` 路由策略或 route 表；主键雪花 | 仅凭 order_no 可查单 |
| S5 | 关单/对账改为分片遍历 | 多库下超时单可关、对账可跑 |
| S6 | 讲解文档：拓扑图、如何切换 profile、限制说明 | 与 `docs/讲解/` 对齐 |

**尽量不改业务 Service 语义**：分片键在现有方法参数中大多已存在（`userId`）；重点改数据源配置、少量 SQL/Job、ID 生成。

## 9. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 复制延迟导致写后读空窗 | 用户体验 | 写后读强制主；列表可读从 |
| 广播表 sold 多库不一致 | 超卖/少卖表象 | 对账纠偏；更新失败重试；演示可先单库广播写校验 |
| 关单全分片扫描 | Job 变慢 | 分片并行 + 批大小；索引 `(order_status, pay_deadline)` 每片保留 |
| 无分片键的管理端查询 | 性能/复杂度 | 强制带 `userId`/`orderNo`；或限制演示接口 |
| 与 MyBatis-Plus 分页插件冲突 | 分页不准 | 单分片分页优先；跨片分页文档标明限制 |
| 默认 profile 被破坏 | 本地开发成本 | **sharding 仅可选 profile**，默认仍单库 |

## 10. 验收标准（设计对应的「代码层完成」定义）

满足以下即视为本期数据库架构升级**代码目标达成**（不必具备生产运维完备性）：

1. 存在可切换的 `sharding`（或同等）配置：至少 2 个数据源，订单按 `user_id` 路由可观察。  
2. 读写分离规则存在：写与「强制主读」路径可说明/可测；从库可配置为真实从或回环主。  
3. 主从在文档与配置中有清晰角色；Compose 或「逻辑主从」二选一可跑。  
4. 建单 / 支付 / 关单在分片模式下主路径可用；对账或关单支持分片遍历。  
5. 默认 `local` 单库行为不被破坏。  
6. 有一份讲解文档说明如何启动与如何验证路由（库名/SQL 日志）。

| # | 选项 | 建议默认 |

| 1 | `tkt_tier` 广播表 vs 独立库存库 | **广播表** |

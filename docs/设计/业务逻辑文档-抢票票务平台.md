## 1. 文档目的

本文档从**业务与规则**视角，描述首期「票档级库存、无选座」场景下的**实体关系、计算公式、状态机、端到端流程、边界条件与异常结果**，供产品对齐、开发与测试编写用例。

- **不写代码、不写接口路径**；技术实现见《技术文档》。  
- **与数据库枚举取值一致**时，直接引用《数据库设计》中的整型状态定义。

## 2. 业务对象与层级

### 2.1 聚合关系

```text
演出 (Show)
  └── 场次 (Session)     ← 用户抢票的时间、开售时间挂在场次上
        └── 票档 (Tier)   ← 价格、库存、限购均以票档为最小售卖单元（首期无座位）
```

### 2.2 交易对象

| 对象 | 说明 |
| --- | --- |
| 订单 (Order) | 用户一次购买行为；关联唯一 `session_id`、`tier_id`；含支付截止时间与应付金额。 |
| 电子票 (Ticket) | 支付成功后按**张**生成；一张票对应订单中的一张座位等价物（首期无座，仅凭证维度按张拆分）。 |

### 2.3 角色

| 角色 | 能力摘要 |
| --- | --- |
| 游客 / 未登录用户 | 仅可浏览公开列表与详情（若产品允许）；**不可抢票**。 |
| 登录用户 | 抢票、支付（模拟）、查本人订单与电子票。 |
| 运营/管理员 | 维护演出/场次/票档；查询订单与统计；关键操作留痕。 |

## 3. 核心概念定义

### 3.1 库存与占用（票档维度）

| 概念 | 定义 |
| --- | --- |
| `total_stock` | 票档配置的总张数，运营录入。 |
| `sold_stock` | **已占用库存**：包含「待支付订单占用的张数」+「已支付订单对应的张数」。不包含已关闭且已释放的订单。 |
| **可售剩余（业务公式）** | `remaining = total_stock - sold_stock`，且 `remaining ≥ 0`。用户可见「余票」可为缓存或异步计算，**允许与真实值短时不一致**，须产品侧标明「仅供参考」。 |

### 3.2 单人限购

| 规则项 | 说明 |
| --- | --- |
| 限购维度 | 同一 **用户** × 同一场次 × 同一票档。 |
| 统计范围（首期约定） | 统计该维度下，处于 **待支付** 与 **已支付** 状态的订单所购买的 **张数之和**（不含已关闭、已退款完成订单）。 |
| 上限 | 不超过票档配置的 `per_user_limit`。 |

**业务意图**：防止单用户通过并发或多笔待支付单突破限购；实现上可配合 Redis 计数 + 数据库校验。

### 3.3 金额

- 单价、总价均以 **分** 为整数存储与计算。  
- **应付总金额** = `unit_price_cent × quantity`，首期无运费、无优惠；若后续扩展优惠券，需单独修订本文档。

### 3.4 支付时限

- 订单创建时生成 **`pay_deadline`**（当前时间 + 配置分钟数）。  
- 用户须在 `pay_deadline` 之前完成支付；**超时则订单业务上视为关闭，占用库存释放回可售池**。

## 4. 状态机

### 4.1 订单状态（`order_status`）

与《数据库设计》一致：

| 值 | 状态 | 业务含义 |
| --- | --- | --- |
| 10 | 待支付 | 抢票成功已生成订单，等待用户支付。 |
| 20 | 已支付 | 用户完成支付（含模拟支付），可生成电子票。 |
| 30 | 已关闭 | 超时未付、用户主动取消（若开放）、或系统关单。 |
| 40 | 已退款（预留） | 首期可不实现退款业务，状态预留。 |

**允许迁移**

| 当前 | 事件 | 下一状态 |
| --- | --- | --- |
| 待支付 | 支付成功 | 已支付 |
| 待支付 | 超时 / 取消 / 关单任务 | 已关闭 |
| 已支付 | — | 终态（首期无退票） |
| 已关闭 | — | 终态 |

**禁止**：已关闭 → 已支付；已支付 → 待支付。

### 4.2 电子票状态（`ticket_status`）

| 值 | 含义 |
| --- | --- |
| 1 | 有效（首期支付成功后默认） |
| 2 | 作废/退票（预留） |

### 4.3 演出状态（`show_status`）

| 值 | 含义 |
| --- | --- |
| 0 | 草稿：不对 C 端展示或仅预览（按产品） |
| 1 | 已发布：可关联已发布场次 |
| 2 | 已下架：不再售卖 |

### 4.4 场次状态（`session_status`）

| 值 | 含义 |
| --- | --- |
| 0 | 草稿 |
| 1 | 即将开售：已配置但未开售 |
| 2 | 开售中 |
| 3 | 停售：运营停售或售罄策略触发 |
| 4 | 场次结束：开场后业务结束 |

**说明**：具体何时从「开售中」自动变为「停售/结束」可由定时任务或开场时间驱动，**须在实现清单中固定一种规则**，本文档仅要求状态语义一致。

### 4.5 票档状态（`tkt_tier.status`）

| 值 | 含义 |
| --- | --- |
| 1 | 上架：允许售卖（仍须满足场次时间与库存） |
| 0 | 下架：不允许新下单 |

## 5. 业务规则矩阵

### 5.1 何时允许「抢票下单」

须**同时**满足：

1. 演出已发布；场次对 C 端可售（状态为即将开售或开售中，具体以产品为准，但至少 **非草稿、非结束**）。  
2. **当前时间 ≥ `sale_start_time`**（开售时间）。  
3. 若配置了 `sale_end_time`，**当前时间 ≤ `sale_end_time`**；未配置则仅受场次状态与库存约束。  
4. 票档已上架。  
5. `remaining ≥ quantity`，且 `quantity ≤ per_user_limit`，且用户在该票档下已占用+已付张数 + `quantity` 不超过 `per_user_limit`。  
6. 未触发风控拒绝（频控、黑名单等，属扩展）。

任一不满足：拒绝下单，返回明确**业务原因**（售罄、未开售、超限购等）。

### 5.2 何时允许「支付」

1. 订单状态为 **待支付**。  
2. **当前时间 ≤ `pay_deadline`**。  
3. 支付人为订单所属用户（所有权校验）。

### 5.3 何时触发「关单并释放库存」

1. 订单待支付且 **当前时间 > `pay_deadline`**：由关单任务或支付接口校验触发。  
2. 业务结果：订单 → 已关闭；`sold_stock` 减少对应 `quantity`；写库存流水（类型：超时释放）。

### 5.4 运营修改规则（首期约定）

| 操作 | 对已生成待支付订单 | 对已支付订单 |
| --- | --- | --- |
| 下调 `total_stock` | 不得导致已合法占用的库存被静默抹除；若新库存低于已占用，**应禁止保存或仅允许后续补偿流程**（实现二选一，须在发布说明中写死）。 | 不得影响；已售出门票有效。 |
| 下调 `per_user_limit` | 一般不追溯已下单；新单须满足新限购。 | 同左。 |
| 票档下架 | 新单拒绝；已有待支付订单可按产品选择「允许继续支付」或「批量关单」，**须固定一种策略**。 |

## 6. 端到端业务流程（业务步骤）

### 6.1 浏览与详情

1. 用户查看演出列表 → 进入场次详情，看到票档价格与**余票参考**。  
2. 若展示「即将开售」，按钮置灰至 `sale_start_time`。  
3. 余票非实时时，文案提示「仅供参考」。

### 6.2 抢票

1. 用户选择票档、张数（默认 1，≤ 限购）。  
2. 系统按第 5.1 节规则校验；通过后创建**待支付订单**并占用库存（`sold_stock` 增加；业务上等同锁定张数）。  
3. 返回订单号、应付金额、`pay_deadline`，前端展示支付倒计时。  
4. **幂等**：同一用户、同一场次、同一票档、同一客户端幂等键下，重复提交应返回**同一笔业务结果**，不产生多笔有效待支付订单（与 DB 唯一约束及实现策略一致）。

### 6.3 支付（模拟）

1. 用户在时限内发起支付。  
2. 校验第 5.2 节；成功则订单 → 已支付，记录支付渠道与时间。  
3. 系统按 `quantity` 生成 **N 张电子票**（每张唯一票号），用户可在「我的票夹」查询。

### 6.4 超时未支付

1. 到达 `pay_deadline` 仍未支付 → 第 5.3 节关单释放。  
2. 用户侧展示订单已关闭；库存可被其他用户抢购。

### 6.5 管理端配置（摘要）

- 维护演出 → 场次 → 票档层级数据。  
- 发布演出/场次前，必填项与状态流转需满足校验（如开售时间早于开场时间，按产品定义）。  
- 关键字段变更写入审计（见需求文档）。

## 7. 库存流水（业务含义）

与 `tkt_stock_ledger.change_type` 对应：

| 类型值 | 业务事件 | 对 `sold_stock` 的影响（约定） |
| --- | --- | --- |
| 1 下单预占 | 订单进入待支付 | 增加 |
| 2 支付确认 | 可选：若需与「预占」区分二次记账；首期可与 1 合并策略，由实现选定 | 视实现 |
| 3 超时释放 | 关单 | 减少 |
| 4 管理端调整 | 人工纠错 | 按单据 |
| 5 对账修正 | 系统自动对齐 | 按单据 |

**原则**：流水应能还原「任一时刻 sold_stock 为何是该值」，便于与订单、对账任务核对。

## 8. 异常与业务结果（面向测试）

| 场景 | 期望业务结果 |
| --- | --- |
| 开售瞬间库存抢光 | 后续请求失败，原因「售罄」或「库存不足」 |
| 用户连点抢票 | 仅一笔有效待支付（或明确返回重复提交与已有订单号） |
| 支付时点刚好跨越 deadline | 以服务端校验时间为准：失败则提示超时，订单进入关闭流程 |
| MQ 延迟导致订单创建晚于用户预期 | 可展示「处理中」；最终仍须满足不超卖与幂等 |
| 余票展示为 1 但提交时售罄 | 允许失败；属最终一致下的正常体验 |
